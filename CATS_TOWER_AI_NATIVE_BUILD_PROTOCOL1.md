# Cat's Tower — AI-Native Build Protocol

## Core loop

`small task → implementation → automated checks → browser/trace/screenshots → AI criticism → repair → Preview → merge`

A task is complete only when its player-facing outcome is observable. Repository activity is not product progress.

## Branch unit

Each branch contains one coherent outcome and targets `kimi`. The PR description records purpose, player-visible result, acceptance, exclusions, evidence and risks. Large mixed changes are rejected.

## Bootstrap gate

The initial scaffold must provide a typed React/Phaser boundary, shared domain package, deterministic fixture, production build, Chromium and WebKit smoke checks, three required mobile viewports, zero uncaught errors and a Vercel Preview.

## First Playable gate

Four cats must run an actual state-driven battle loop:

`move → telegraph → attack → hit → damage → defeat → reward → level-up → next enemy`

Required: deterministic replay, pause/resume, three-minute soak, readable 320×568 layout, visible cause and effect, and physical-iPhone feel review.

## Vertical Slice gate

Expand only after First Playable approval. Complete launch through 10F boss and 11F connection with recovery, save, representative production assets and shared runtime/simulation operations.

## Asset rule

Do not generate the full cast. Prove one melee cat, one ranged cat, one enemy, one boss, one district background, core UI and hit/reward VFX in-engine first.

## Trust boundary

Prototype coin may be local and visibly labelled. Account, paid/free ruby, gacha, ownership, duplicate/mastery, evolution, tower return, purchase and refund are server-authoritative before production acceptance.

## Evidence

CI must preserve build output, successful viewport screenshots and failure traces. AI must inspect the output rather than accepting a status badge. Physical-device and Production claims require their own evidence.
