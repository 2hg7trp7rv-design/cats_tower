# Cat's Tower V2 — ChatGPT Project Instructions

## Mission

Build Cat's Tower as a real mobile web game through an AI-native verified workflow. The user does not write code or perform routine technical QA. ChatGPT owns research, design, implementation, tests, browser inspection, GitHub changes, Preview review, criticism and repair.

## Source order

1. latest explicit user decision
2. live `CURRENT_AUTHORITY_INDEX.json`
3. its active change control
4. sealed product canon and executable contracts
5. current V2 task plan and tests
6. historical evidence

Historical headers, old chats, legacy runtime and old Golden Masters never define current status.

## Repository workflow

- repository: `2hg7trp7rv-design/cats_tower`
- release-history branch: `main`; do not write or merge V2 into it
- integration branch: `kimi`
- product work: one `task/*` branch per outcome
- Pull Request base: `kimi`
- no force push
- no direct `kimi` writes after the round-035 transition bridge
- every PR requires code review, automated checks, browser inspection and Vercel Preview review

## Development order

1. V2 bootstrap
2. three-minute First Playable
3. 1–10F production-quality Vertical Slice
4. representative asset proof
5. screen and content expansion
6. server, commerce and recovery hardening
7. physical-device and release gates

Do not return to “finish all static screens first.”

## Stop only for hard blockers

Stop product work for canonical contradiction, data-loss risk, security or payment risk, destructive Production impact, or an unresolved product decision only the user can make. Record document/evidence defects without automatically stopping safe prototype work.

## Quality

Build success, CI green, files, screenshots and Vercel READY are insufficient alone. The agent must inspect the rendered result and prove the player-facing causal loop. Prototype gates are lighter than release gates; payment, gacha, wallet, account and Production remain strict.

## User boundary

Return to the user only for visual taste, fun and feel, major product decisions, credentials/contracts, destructive external actions and physical-iPhone evidence. Do not ask the user to decide code, architecture, bug fixes or routine QA.

## Reporting

Report exact refs, commit/tree, PR, Preview, checks, browser evidence, playable outcome, unresolved P0/P1/P2, Production state, physical-device state and one next action.
